# Body tracker — notes for Claude Code

## Core tenets (apply to every change)
1. **Simplicity**: the fewest messages, words and taps that do the job. Prefer removing to adding; fold detail behind tap-to-expand.
2. **Toothbrush test**: it must become a daily reflex he never thinks about (one morning tap, one evening recap, voice in between).
3. **Value**: every message must be worth reading; if it isn't, don't send it.
A feature that fails any of the three doesn't ship, however clever.

Personal Telegram bot + dashboard on Vercel (plain Node functions in `api/`, no framework; static `public/index.html`).
Storage: Postgres on Neon (`DATABASE_URL`, via the Vercel Marketplace), see `lib/store.js`: tables events (one row per event, JSONB), measurements, docs (small mutable docs: owner, profile, equipment, bests, pin, msgmap…), seen (dedupe keys), photos (base64). Tables are created on first use. The old Vercel Blob store hit the Hobby quota (Nov 24, 2026: blob-as-database used ~10k reads in 6 days) and was suspended; `lib/blobstore.js` is kept only so the nightly job can import that history once the quota resets (doc `legacy_imported` marks it done; manual: `/api/admin?import_legacy=1`). Claude API via fetch (`lib/claude.js`).

## Repo and deploys

## First deploy
Run `bash setup.sh` (asks for the Telegram bot token and Anthropic key, generates the rest, deploys, registers the webhook).
If the user already deployed an earlier version: just `npx vercel deploy --prod`. Data from v1 is compatible (old workout format is read by `setsOf`).

## Key files
- `lib/plan.js` — training plan as data: sessions per weekday, exercises (id, target, `track`, `levelTracks`, `repsTop`, `inc`), blocks calendar, skill ladders.
- `lib/training.js` — ladders, PRs, progression hints, adherence, sets per muscle, plan card.
- `lib/claude.js` — food vision prompt and the text parser prompt (`textSystem`), which maps free text to plan ids.
- `api/telegram.js` — webhook; `api/morning.js` (cron 05:30 UTC: one check-in ping), `api/evening.js` (cron 19:30 UTC = 21:30 Cairo: daily recap + voice note; on Sundays the stored weekly review folds in), `api/weekly.js` (cron Sun 05:00 UTC: silent housekeeping + stores weekly recap, diet review, habit tips) and `api/nightly.js` (cron 21:30 UTC: silent self-improvement loop); `api/data.js` feeds the dashboard; `api/steps.js` (= `api/health.js`) receives Health Auto Export: steps, sleep, resting HR, HRV. Recovery signals and flags live in `lib/recovery.js`. (`api/migrate.js`, the one-time public→private copy, has been removed.)

## Debugging
- Runtime logs: `npx vercel logs <deployment-url>` or the Vercel dashboard.
- Test the crons by hand with the `x-dashboard-key` header: `/api/morning?dry=1`, `/api/evening?dry=1`, `/api/nightly?dry=1` (previews, nothing sent or applied). `/api/weekly` has no preview: it writes.
- Errors in the bot are also sent back to the chat as "Error: …".
- Adaptive plan: `lib/adapt.js` stores `week_plan` events; `dayPlan()` prefers them over `lib/plan.js`. Voice notes: `lib/voice.js` (Groq Whisper, needs `GROQ_API_KEY`).
- Diet: `lib/diet.js` — weekly Sun–Sat budget (with a cheat-meal reserve, `CONFIG.cheat`) rebalances the daily target (`todayTarget`), Sunday/`/diet` review estimates maintenance from intake + weight trend and stores a `diet_plan` (target from phase `rate` in `lib/config.js`).
- Dashboard (`public/index.html` + `api/data.js`): flags, adjusted 7-day plan, Sun–Sat diet week + weekly review, recovery (sleep, Elite HRV rMSSD, RHR, wood/energy/knee).
- Persona + memory: `lib/persona.js` (shared voice, profile doc of lasting facts; "remember" parser kind; Sunday consolidation; `chat` events give follow-up context). All Telegram text goes through `lib/format.js` (markdown → Telegram HTML, plain-text fallback).
- Photos: FOOD schema classifies image_kind (food/body/other); body photos → `savePhoto` in the private store (never on the dashboard), `/compare` (`lib/progress.js`), `/photos`, `/deletephotos`. Morning line asks for weight; Sundays ask for tape, every 2nd Sunday for photos.
- Food accounting: the parser also sees yesterday's entries numbered 101, 102… (`foodByNumber`), so late corrections replace them and keep their date. Tapping ✏️ Fix stores doc `fixing` {ts}; the next message within 15 min replaces that entry (never a new one). Earlier bug (Nov 26): a Fix reply to a yesterday entry created a new today entry, then "that was yesterday" moved it, double counting.
- Food accounting: the text parser sees today's numbered food list and returns food (action new/replace + replaces), food_day (restated day → replaces all today), or food_delete. Edited Telegram messages correct their own entry (`msg_id`). `markSeen` dedupes Telegram re-sends. `/today` numbered list, `/reset` clears today.
- `api/admin.js`: POST set_food replaces a day's food with an exact list (manual repairs).
- Habits: `lib/habits.js` clusters food items into staples (most logged days) vs occasional; tips from Sunday or /habits (`habit_tips` event) show when a matching meal is logged, once a day each.
- Form cues: `lib/cues.js` (only the ~20 most error-prone exercises), inline in session/morning cards; adjusted plans add `cue` only where needed.

## Programme v2 (from the "Training Schedule — Cut, Skills & Ski Prep" doc)
- `lib/plan.js`: gym sessions A→B→C→D and home H1→H2→H3 run in ORDER (next after the last logged one; future days projected over the sample week `WEEK`). B/H2 a day apart (`homeFor` swaps H2→H3). Taper halves B/H2 and drops skater hops; deload halves sets. Rucks via `ruckKg`. `MILESTONES`, `TESTS`, ladders updated.
- Calorie cycling (`lib/config.js` phase `cycling`, `lib/diet.js` `cyclingTarget`): low 1,500 / high 2,700 on gym B/D days (home versions and skipped B/D stay low) or a planned feast (`feast_plan` event, parser kind `feast`, cap 3,200), max 2 high days (3 with a stop sign), week ~13,500. Flat phases (ski break, January check) keep the weekly rebalancing.
- Morning (`api/morning.js`, `?dry=1` previews): superseded by the v3 rhythm below. Workout card on request ("workout" / parser `show_plan`) or at the learned training hour (`lib/schedule.js` `usualHour`, sent by `api/nudge.js`, 12 daily crons 08:00–19:00 Cairo).
- Equipment: `lib/equipment.js` (lists per place in `docs/equipment.json`, home seeded); parser kind `location` saves lists and, with train_here, rewrites the day's gym session as a one-day `week_plan` (keeps the session letter). Preview: `/api/admin?key=…&preview_place=home&session=B`.
- Parser debugging: every text message is stored as an `inbound` event with how it was read; `/api/admin?key=…&parse=<text>` shows how a message would be read without acting. The parser gets TODAY'S STATE (e.g. session already rebuilt for home) so "regenerate it" works.
- Workout logging: "done as planned" fills exercises of today's plan (incl. home version) via `plannedSets`; skipped ones are left out; exercises already logged today are not logged twice; home-variant logs carry `place` and never become the gym's "last time". Rebuild requests are weighed against `programmeCoverage()` (where each muscle is trained in the week).
- Messages can hold several things: the parser returns `{entries:[…]}` and the webhook dispatches each. Workouts are logged as changes from the plan (`logWorkout` merges into the day's logged workouts; `date` for "yesterday"). Morning = separate texts (day+insight, check-in, tape/milestone); after the check-in (any hour) come the routine card and a short "today" text; workout nudges default to 16:00 gym / 18:00 home until learned. Admin repair: POST `{action:"drop_exercise", date, plan_id}`.
- CAUTION when editing api/telegram.js with scripted slices: helper functions (parseText, showPlan, saveProgress, logRecovery) sit between logWorkout and replan; slice by function boundaries, not by "next function name".
- Storage reads: everyday paths use `recentDays(21)` (one query; adds a synthetic `bests` event from the `bests` doc). Only the weekly job, the nightly loop and `/api/data` call `allEvents()`. `rollupMonths` is a no-op kept for callers.
- Native Telegram UX: `lib/tg.js` (buttons, edit, react, pin, silent, voice). Replies to him are silent by default (`send` wrapper in api/telegram.js); crons buzz only for actionable texts. Inline buttons: check-in (`c:`), workout card (`w:plan|chg|skip|home`), food (`f:ok|fix|undo:<ts>`), unclear messages (`u:`); handled in `handleCallback`. Pinned daily status: `lib/today.js` `refreshToday` (doc `pin`), refreshed after every log. Food corrections edit the original bot message (doc `msgmap`). Long texts fold with `<blockquote expandable>` (`fold`/`foldLong`). Snooze → doc `nudge_override`. Setup (`/api/setup?keyboard=1`) registers commands + bottom keyboard. Voice output (`speak`/`wavToMp3`) exists but is not used: the evening voice note was removed (it did not earn its place).
- Session choice: "push day today" / picker buttons (`s:<key>`, `p:gym`) store a `session_choice` event; `sessionFor`/`homeFor`/`dayPlan` honour it (training day, order continues from it). On a rest day, "I'm training today" offers the next session in order with a picker.
- Coach rhythm (v3): morning = ONE check-in ping (wood tap only); after the check-in ONE `todayText` (shape + nightly focus + routine folded). Evening 21:30 = `eveningRecap` (how today went, one win, one adjust, tomorrow's first move) + missing steps/workout. No copy-paste <pre> blocks anywhere. Pinned status is one line with an expandable body.
- Nightly loop `lib/improve.js` via `api/nightly.js` (21:30 UTC, silent; `?dry=1` previews): reviews all history and may write `week_plan` (source nightly, same session letters), `routine_plan`, `diet_tweak` (bounded) and always a `coach_log` (summary, focus, rationale) that the persona reads to explain changes. Goals in config/plan are fixed.
- Habit layer `lib/habit.js`: day N of 20, streaks, capped silent nudges in `api/nudge.js` (10–11h check-in, 14–15h food) only during onboarding or after a miss and never if active in the last 90 min; streak notes at 3/7/14/20.
- His style (also saved to the coach's memory): short, one topic per text, voice-first, no copy-paste blocks, corrections replace entries, nothing intrusive. Previews of crons that can send must use `?dry=1`; a request can hit the previous deployment for a few seconds after a deploy, so wait ~30 s before previewing.
- Weekly report: `lib/report.js` (pdfkit, built-in fonts, Latin-1 only via `safe`): goals (fixed), where he is, week numbers + calorie chart, key skills, "how I tailored your plan" (coach_log rationales, diet/routine tweaks, home rebuilds, picks). Sent with the Sunday evening recap only after a `solidWeek` (≥5 check-ins, ≥5 food days, ≥4 sessions); on request via "send my report" / /report; "what were my goals / what changed" → text (`goalsAndChanges`). Preview: `/api/admin?report=1` returns the PDF.
- Bare "done": the bot records what it last asked for (doc `last_prompt`: checkin / routine / workout / evening) and the parser maps "done" to it; a bare "done" never logs a gym session unless the last prompt was the workout; otherwise "Done with which one?" buttons (`r:done` / `w:plan:<key>`).
- Dated logging: FOOD has `date` ("yesterday's dinner"); "this is for yesterday" replaces (moves) that entry. Steps already take a date. Admin repairs: POST `{action:"redate", path, date}` and `{action:"add", type, data, date}`.
- Treadmill → steps: `lib/walk.js`. A logged treadmill walk is converted (≈1,400 steps/km, else speed × time, else 100/min) and added to the day's steps; each steps event stores `steps` (total) = `base` (phone/typed) + `extra` (treadmill, recomputed from the day's workouts so corrections never double count). A later typed total keeps the extra unless he says it includes the treadmill (`includes_treadmill`). Apple Health totals replace as before.
- Plan diff: `lib/plandiff.js` (`planDiff`, `daysVsPlan`) compares a day's logged exercises with that session's plan: missed, swaps (same muscle; walks never swap for intervals, tracked skills never count as swapped), extras. `logWorkout` stores `vs_plan` (not shown to him); the nightly loop recomputes it for every trained day (`vsPlan` in its context) and moves missed key work into the next suitable gym day.
- Day calorie target: the nightly loop may set tomorrow's target (`tomorrow_kcal` → `day_target` event {target_date, kcal, why}, bounded low−200…high+200, never on a feast day) from what actually happened; `cyclingTarget` honours it if the week still fits (week budget +300) and uses it for that day's expected/high count.
- Workout reply = ONE line (his call, Nov 26): `🏋️ D logged · 5 exercises` + only what changes his day: 🏆 PR, 🍽 new same-day target, 👟 treadmill steps, or "sets for X?". No plan diff, hints, milestone gap, flags or footer; Undo button stays.
- Engagement v4 (`lib/engage.js`), all rule-based:
  - Act first: the parser logs anything carrying data even when phrased as a question; workout and treadmill-steps replies carry a one-tap `↩️ Undo` (`x:<path>`; workout undo also re-syncs steps and drops its same-day calorie correction).
  - Usual meals: a meal (same slot, similar items) seen on 2+ of the last 14 days shows as a one-tap button under the Today card (`q:<ts>` copies it to today via `logFood`).
  - Same-day calories: logging a high (B/D) day whose legs/intervals were skipped lowers today's target (`sameDayKcal`: done 1, swapped 0.5, missed 0, legs/cardio count double; ≥80% keeps it) as a `day_target` with `source: same_day`; completing later restores it.
  - Week commit: Saturday's recap sends a day picker for the coming Sun–Sat (`k:<date>` toggles, `k:ok` locks → `week_commit`); `/gymdays` does it for the rest of this week. `isGymDay` (plan.js) makes the session order, gym-day flag, nudges and calorie cycling follow it.
  - Never miss twice: `slipLine` on the Today card after a missed gym day; habit nudges after a miss offer the minimum version; a comeback note after a missed check-in. No streak-broken messages.
  - Ski countdown (`countdownLine`, from the ski phase in config) + legs this week on the Today card (`milestoneGap` exists but is no longer shown in the workout reply).
  - Weekly report: a private "Then and now" page when this week has a progress photo and one is 4+ weeks older.
- Parser regression set: `tests/parser-cases.json` (every phrase that was once misread) via `DASHBOARD_KEY=… node tests/parser-check.mjs` against the deployed `/api/admin?parse=`. Run after every deploy; add a case for every new misread.
- API wrapper (`lib/claude.js` `ask`): `system` may be `[stable, volatile]`: the stable part is cached (`cache_control` ephemeral; the parser's rules + catalog ≈5.5k tokens are read from cache on repeat messages within ~5 min); `cache: true` caches a plain string (food photo prompt). Keep anything that changes per message (date, today's state/food) OUT of the stable part or the cache never hits. Server-side fallback (`anthropic-beta: server-side-fallback-2026-07-01`, `fallbacks: "default"`) retries a declined request on a fallback model. Models: `CONFIG.model` (Sonnet 5.5) for everything per-message, `CONFIG.reviewModel` (Opus 5.5) for the nightly review. Check caching with `/api/admin?parse=…&usage=1` (second call shows `cache_read_input_tokens`).
- Conversation log: every bot message is stored as `outbound` (in `lib/tg.js` send/edit), every text as `inbound`; misread signals (`misread`: food Fix/Undo taps, workout/steps Undo, texts starting "no / I meant / you misread…") store the message that caused them. All are debug types skipped by normal reads (`debugLog(days)` reads them). Views: `/api/admin?log=7` (timeline in/out) and `/api/admin?misreads=14` → turn each real misread into a case in `tests/parser-cases.json`.
- Spend (Nov 28: credits ran out after ~9 of his messages in 3 days; most spend was dev testing + the nightly review): every API call logs `api_usage` {tag, model, tokens, usd} (debug type); `/api/admin?spend=7` = cost per day and feature. `CONFIG.dailyBudgetUsd` (0.40): past it, optional calls are skipped (nightly review, evening recap prose); parsing and photos always run. Nightly review runs only if something was logged since the last one, Opus at medium effort. Efforts: parser low, photos/chat medium, recaps low.
- Testing costs real credits: run `tests/parser-check.mjs --only=<regex>` for the cases a change touches; the full set only for parser/prompt changes. It runs sequentially so the cache is warm (never in parallel). Avoid repeated `?dry=1` previews of the nightly (Opus) and evening jobs.
